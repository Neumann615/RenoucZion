# AI 核心术语通俗指南

> 一次性讲明白 Agent、Skill、Harness、MCP、RAG、Tool 等 AI 技术名词的含义与关系

## 前言

随着 AI 技术快速演进，各类新名词层出不穷：Agent、Skill、Harness、MCP、RAG、Tool Use... 它们在社区、技术文章、招聘 JD 中反复出现，容易让人混淆。本文从**最通俗的角度**出发，帮你一次性理清这些概念的含义、区别和关系。

---

## 一、一句话概览

| 概念 | 一句话解释 | 类比 |
|------|-----------|------|
| **Agent（智能体）** | 能自主思考、拆解任务、调用工具、自我纠错的 AI 系统 | 一个完整的人 |
| **Harness（运行框架）** | 包裹在模型外部的整套运行管控体系 | 后厨管理体系 |
| **Skill（技能）** | 封装好的专业能力包，告诉 AI 某件事怎么做 | 一本菜谱 |
| **Tool（工具）** | AI 调用外部系统的具体操作（API、数据库、文件系统等） | 锅碗瓢盆 |
| **MCP（模型上下文协议）** | 统一 AI 连接外部工具的标准协议 | USB-C 接口 |
| **RAG（检索增强生成）** | 先查资料再回答，杜绝 AI 瞎编 | 开卷考试 |

---

## 二、核心概念详解

### 🤖 Agent（智能体）

**核心定义**：能在环境中采取行动、观察结果、并根据反馈自主决策的 AI 系统。

Agent 跟普通聊天机器人最本质的区别：

| | 普通大模型（Chat） | Agent |
|---|---|---|
| 交互模式 | 一问一答（One-shot） | 思考→行动→观察→再思考→...（Loop） |
| 能力边界 | 只能输出文本 | 能调用工具、执行代码、操作文件 |
| 纠错能力 | 没有 | 发现错误 → 自己改正 |
| 任务粒度 | 单次对话 | 端到端完成复杂任务 |

**Agent 的工作流程**：

```
用户需求 →
  思考（分析任务）→
    选择工具（该用什么？）→
      执行（调用 API / 读写文件 / 运行代码）→
        观察结果（成功？失败？）→
          反思（哪里可以改进？）→
            继续执行... →
              ✅ 任务完成
```

**实际例子**：你让 Agent "帮我写一个登录页面"——

1. 分析需求：需要表单、验证、样式
2. 创建 `Login.vue` 文件
3. 写完代码
4. 打开浏览器预览
5. 发现布局不对 → **自己修改 CSS**
6. 再预览 → 满意 → ✅ 完成

> **核心能力：自主决策 + 自主纠错 + 闭环完成任务。**

---

### ⚙️ Harness（运行框架 / 挽具）

**核心定义**：独立于大模型之外，由代码、配置、执行规则组成的**运行管控体系**。

这是 2025-2026 年 AI 工程化最核心的概念。有一个广泛引用的等式：

> **Agent = Model + Harness**
>
> *"If you're not the model, you're the harness."* — Viv Trivedy

**Harness 包含什么？**

| 组件 | 作用 | 具体示例 |
|------|------|---------|
| **指令层** | 明确任务边界和约束 | 系统提示词、Rules、AGENTS.md、CLAUDE.md |
| **工具层** | 管理 AI 能调用哪些工具 | MCP Server、CLI 沙箱、Bash 权限、浏览器 |
| **状态层** | 记录任务进度 | 上下文管理、记忆层、对话历史压缩 |
| **观测层** | 全流程行为留痕 | 日志、trace、token 消耗统计 |
| **评估层** | 客观验收标准 | 测试是否通过、编译是否成功、lint 检查 |
| **约束层** | 拦截高危操作 | 命令白名单、人工审核节点、权限分级 |
| **反馈层** | 把错误转化为经验 | "这次错了 → 下次永不再犯" |
| **编排层** | 协调多个 Agent | 子 Agent 派生、任务分发、模型路由 |

**一个关键案例**：LangChain 团队将一个编程 Agent 的性能从 **Top 30 提升到 Top 5**（分数从 52.8% → 66.5%），**仅仅改了 Harness，模型完全没换**。改动包括：自我验证清单、启动时扫描目录结构、死循环检测中间件、推理预算策略。

> **核心理念：模型决定能力上限，Harness 决定稳定下限。两者之间的差距，就是工程化的差距。**

---

### 📗 Skill（技能）

**核心定义**：可复用的"能力包"——本质是一个包含指令、参考文档、脚本的结构化文件夹。

**为什么需要 Skill？**

想象你每次让 AI 做 PR 审查，都要手打一大段话：

> "帮我审查这个 PR，要检查：1）代码风格是否符合团队规范，2）有没有潜在 bug，3）测试覆盖够不够，4）安全性有没有问题..."

太累了。**Skill 就是把这段话打包成一个文件**，以后 AI 看到相关任务会**自动加载**。

**一个 Skill 的结构**：

```
order_query_skill/          # 订单查询技能
├── SKILL.md                # 核心指令文件（AI 的行为指南）
├── query_template.sql      # 数据库查询模板
├── sample_data.json        # 测试数据
└── hooks/                  # 扩展点
```

**Skill 的三大特点**：

- 🧩 **模块化**：可以热插拔，需要时加载，不用时不影响
- 📋 **结构化**：不是散乱的提示词，而是标准格式
- 🔄 **可复用**：写一次，跨项目、跨平台使用

**Skill vs Tool 的区别**：

| | Tool（工具） | Skill（技能） |
|---|---|---|
| 粒度 | 单一操作（原子级） | 多个操作的组合（方案级） |
| 举例 | `browser_click`、`read_file` | "小红书自动发布" = 浏览器操作 + 登录逻辑 + 发布流程 + 异常处理 |
| 类比 | 螺丝刀 | 装修套餐 |

---

### 🔌 MCP（Model Context Protocol，模型上下文协议）

**核心定义**：由 Anthropic 于 2024 年 11 月开源的开放标准协议，统一了 AI 模型与外部工具/数据源的连接方式。

**通俗类比**：

> MCP 之于 AI 工具 = **USB-C 之于电子设备**

在 USB-C 出现之前，每个设备需要不同的数据线。MCP 出现之前，每个 AI 平台（ChatGPT、Claude、Gemini）各有各的工具接口标准，开发者需要为不同平台**重复开发同一套工具**。MCP 让**一次开发，到处能用**。

**MCP 的架构**：

```
┌────────────────────────────────────────────┐
│          MCP Host（AI 应用）                 │
│  例如：Claude Desktop、Cursor、VS Code       │
│                │                            │
│          MCP Client（协议客户端）              │
│                │                            │
│    ┌───────────┼───────────┐                │
│    ▼           ▼           ▼                │
│  MCP        MCP         MCP                │
│  Server A   Server B    Server C           │
│  (文件系统)  (数据库)     (GitHub API)       │
└────────────────────────────────────────────┘
```

**MCP Server 能暴露什么？**

- **Resources**（资源）：暴露数据，如文件内容、数据库记录、API 响应
- **Tools**（工具）：暴露可执行操作，如发送邮件、创建 Issue、查询天气
- **Prompts**（提示模板）：预定义的交互模板，如"代码审查"、"生成周报"

> **大白话**：MCP = AI 工具的"通用插座"，打破不同系统之间的连接壁垒。

---

### 📚 RAG（Retrieval-Augmented Generation，检索增强生成）

**核心定义**：让 AI 在回答问题之前，先从一个知识库中检索相关内容，再基于检索结果生成回答。

**通俗类比**：

> **开卷考试 vs 闭卷考试**

- 传统大模型 = **闭卷默写**：只靠训练时记住的知识，容易"幻觉"（瞎编）
- RAG = **开卷考试**：先翻书查资料，再作答，回答有据可依

**RAG 的工作流程**：

```
用户提问："公司年假政策是什么？"
    ↓
① 检索（Retrieval）
   └→ 从公司内部知识库搜索相关文档片段
    ↓
② 增强（Augmented）
   └→ 把检索到的文档片段 + 用户问题拼接在一起
    ↓
③ 生成（Generation）
   └→ 大模型基于上下文生成答案：
      "根据公司政策，入职满1年的员工享有5天年假..."
```

**典型应用场景**：

- 智能客服：查产品手册回答用户问题
- 企业知识库：问答内部文档、规章制度
- 金融分析：引用最新研报和财报数据
- 法律咨询：基于法规条文给出建议

> **大白话**：RAG 解决了 AI "胡说八道"的问题，让回答有据可依。

---

### 🔧 Tool / Function Calling（工具调用）

**核心定义**：让大模型能调用外部 API 来执行实际操作，是 AI 从"会说话"到"会干活"的关键桥梁。

**通俗类比**：

> AI 以前只会"动嘴说"（输出文本），有了 Tool 就能**动手做**——像给大脑接上了手脚。

**工具调用的流程**：

```
① 开发者定义工具
   {
     name: "send_email",
     description: "发送一封邮件",
     parameters: { to: "收件人", subject: "主题", body: "内容" }
   }

② 用户说："帮我给张三发邮件，告诉他会议改到明天下午3点"

③ 大模型判断：需要调用 send_email 工具
   输出：{"function": "send_email", "parameters": {"to": "zhangsan@example.com", ...}}

④ 程序执行：实际调用邮件 API

⑤ 返回结果给大模型："邮件已发送成功"
```

**常见的 Tool 类型**：

| 类别 | 示例 |
|------|------|
| 网络 | 搜索网页、调用 REST API、爬取数据 |
| 文件 | 读取、写入、搜索代码文件 |
| 数据库 | 执行 SQL 查询、读写记录 |
| 系统 | 执行 Shell 命令、管理进程 |
| 通信 | 发送邮件、Slack 消息、创建 Issue |
| 浏览器 | 点击元素、填写表单、截图 |

> **没有 Tool，Agent 只能是空想家。有了 Tool，Agent 才能把想法付诸行动。**

## 三、各概念之间的关系

### 层次关系

```
┌──────────────────────────────────────────────────┐
│                   Agent（智能体）                   │
│                                                   │
│  ┌─────────────────────────────────────────────┐ │
│  │              Harness（运行框架）               │ │
│  │                                              │ │
│  │  ┌─────────────────────────────────────┐    │ │
│  │  │      Think → Act → Observe 循环      │    │ │
│  │  │                                      │    │ │
│  │  │   ┌──────────┐   ┌──────────────┐   │    │ │
│  │  │   │  Model   │ → │  Tool 执行    │   │    │ │
│  │  │   │ （大脑）   │   │ （手脚）       │   │    │ │
│  │  │   └──────────┘   └──────────────┘   │    │ │
│  │  └─────────────────────────────────────┘    │ │
│  │                                              │ │
│  │  Rules / Skills / AGENTS.md（指令层）         │ │
│  │  MCP Servers（工具层）                        │ │
│  │  CLI 沙箱 / 权限模型（约束层）                  │ │
│  │  上下文管理 / 记忆层（状态层）                   │ │
│  │  测试 / Lint / Hook（验证层）                  │ │
│  │  监控 / Trace / 日志（观测层）                  │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘

         MCP 协议 ── 统一连接 ──→  Tool₁  Tool₂  Tool₃  ...
                                      ↑       ↑       ↑
                                    外部 API  数据库  文件系统

         RAG ── 知识增强 ──→  知识库 / 搜索引擎 / 内部文档
```

### 依赖关系

```
Skill（技能包）
  ├── 包含 Tool（工具）的调用逻辑
  ├── 通过 MCP（协议）连接外部系统
  └── 可配合 RAG（检索）增强知识
        │
        ▼
     Agent（智能体）调度 Skills
        │
        ▼
     Harness（框架）提供运行保障
```

## 四、AI 工程化演进三阶段

理解这些概念，最好放在 AI 工程化的演进时间线中看：

| 阶段 | 核心问题 | 代表性概念 | 时间 |
|------|---------|-----------|------|
| **Prompt Engineering**（提示词工程） | "怎么问 AI 才有效？" | Few-shot、Chain-of-Thought、角色设定 | 2023 |
| **Context Engineering**（上下文工程） | "AI 应该看到什么信息？" | 动态上下文管理、记忆系统、工具描述注入 | 2024-2025 |
| **Harness Engineering**（挽具工程） | "AI 跑在什么样的系统里？" | 约束验证、错误恢复、反馈闭环、Hook 机制 | 2025-2026 |

> **三阶段不是替代关系，而是叠加关系**——每个阶段都建立在前一个阶段之上。

**关键趋势**：行业重心已经从"拼模型谁更聪明"转向了"拼谁能让 AI 在真实业务中**稳定落地**"。这就是为什么 **Harness Engineering** 成为 2026 年最重要的 AI 工程概念。

## 五、对比总结表

| 对比维度 | Agent | Skill | Harness | MCP | RAG | Tool |
|---------|-------|-------|---------|-----|-----|------|
| **定位** | 决策层 | 功能层 | 运行层 | 协议层 | 知识层 | 执行层 |
| **核心问题** | 如何自主完成任务 | 如何高效执行单一任务 | 如何规模化管控 AI | 如何统一连接工具 | 如何让回答准确 | 如何操作外部系统 |
| **类比** | 一个人 | 一本操作手册 | 交通管理系统 | USB-C 接口 | 开卷考试 | 螺丝刀 |
| **独立性** | 可独立运行 | 依赖 Agent 调度 | 为 Agent 提供环境 | 标准协议规范 | 依赖知识库 | 被 Agent 调用 |
| **粒度** | 系统级 | 方案级 | 平台级 | 接口级 | 数据级 | 操作级 |

## 六、记忆口诀

> **Agent** 是干活的人，**Harness** 是管人的制度，
> **Skill** 是手里的说明书，**Tool** 是手里的家伙，
> **MCP** 是统一的插座，**RAG** 是翻书的习惯。
